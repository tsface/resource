# ClickHouse 查询执行流程与核心数据结构

ClickHouse 从 SQL 解析到最终执行计划的生成，是一个经典的 **解析 (Parsing) -> 逻辑计划 (Logical Planning) -> 物理计划/流水线 (Physical Planning/Pipeline) -> 执行 (Execution)** 的过程。

我们以一个简单的查询为例来贯穿整个流程：
```sql
SELECT id, name FROM default.users WHERE age > 18
```

以下是该流程的几个核心阶段，以及对应的底层核心数据结构（基于 ClickHouse 最新的 Pipeline 和 QueryPlan 架构）：

### 阶段一：SQL 解析阶段 (Parsing)
在这个阶段，纯文本的 SQL 字符串会被解析成**抽象语法树 (AST)**。

*   **入口点：** `parseQuery` 函数。
*   **核心数据结构：**
    *   **`IParser`**: 解析器接口。ClickHouse 是手工编写的递归下降解析器（Recursive Descent Parser），而不是用 Bison/Yacc 等工具生成的。
    *   **`IAST`**: 所有抽象语法树节点的基类指针（通常表现为 `ASTPtr`）。
    *   **`ASTSelectQuery`**: 专门用于表示 `SELECT` 查询的 AST 节点。它包含多个子节点指针，例如 `select()` (投影列), `tables()` (FROM 子句), `where()` (过滤条件)。
    *   **其他 AST 节点**: 在我们的例子中，`id` 和 `name` 会变成 `ASTIdentifier`；`age > 18` 会变成一个 `ASTFunction` (函数名为 `greater`)，它的参数是 `ASTIdentifier(age)` 和 `ASTLiteral(18)`。

### 阶段二：解释与逻辑计划生成阶段 (Interpreter & Logical Planning)
在这个阶段，AST 会被转换为**逻辑查询计划 (QueryPlan)**。不仅进行语法分析，还会进行语义分析（如验证表是否存在、解析列类型、解析别名等）。

*   **入口点：** `InterpreterFactory::get(...)` 获取对应的 Interpreter。
*   **核心数据结构：**
    *   **`IInterpreter`**: 解释器基类。对于 `SELECT` 语句，具体的实现是 **`InterpreterSelectQuery`**。它负责协调整个语义分析和计划生成过程。
    *   **`TreeRewriter` / `ExpressionAnalyzer`**: 负责执行语义分析的组件。它们会将 AST 里的表达式展开，解析函数的真实数据类型（利用底层的 `IDataType` 和 `Column` 知识），并准备好执行表达式所需的动作集合。
    *   **`QueryPlan`**: **逻辑查询计划树**。这是一个由逻辑步骤组成的有向无环图 (DAG)。它描述了“要做什么”，但不描述“具体怎么多线程执行”。
    *   **`IQueryPlanStep`**: 逻辑计划树上的节点（步骤）。在我们的例子中，`InterpreterSelectQuery` 会在 `QueryPlan` 中自底向上生成如下 Steps：
        1.  **`ReadFromMergeTree`** (继承自 `ISourceStep`): 从 `default.users` 读取数据的逻辑步骤。
        2.  **`FilterStep`**: 接收数据，并应用 `age > 18` 的过滤逻辑。
        3.  **`ExpressionStep`**: 计算并只保留最终需要的列 `id` 和 `name`。

### 阶段三：物理执行计划/流水线构建 (Physical Pipeline Building)
逻辑计划 `QueryPlan` 会被转化成底层向量化执行引擎能够直接多线程调度的**物理查询流水线 (QueryPipeline)**。

*   **入口点：** `QueryPlan::buildQueryPipeline(...)`
*   **核心数据结构：**
    *   **`QueryPipeline` (或 `QueryPipelineBuilder`)**: **物理执行计划**。它不再是简单的逻辑树，而是由众多具体执行单元（Processors）及其相互连接的数据流通道组成的复杂网络。
    *   **`IProcessor`**: ClickHouse 向量化执行引擎的核心处理单元。Processor 有输入端口 (`InputPort`) 和输出端口 (`OutputPort`)。
        *   **`ISource`**: 如 `MergeTreeBaseSelectProcessor`。如果表有多个 Part，Pipeline 会实例化多个 Source 并发读取（多线程读取）。
        *   **`ISimpleTransform`**: 如 `FilterTransform`。接收上游数据，过滤掉 `age <= 18` 的行，将结果输出。
        *   **`ISink`**: 消耗最终数据的终端节点。
    *   **`Pipe`**: 构建 Pipeline 时的辅助结构，可以将多个单线程的 Processor 组合成一个多线程的执行管道，方便进行诸如 `ResizeProcessor` (线程数合并/分裂) 的操作。

### 阶段四：执行阶段 (Execution)
流水线构建完成后，执行器会调度这些 Processors 在线程池中流式运转。

*   **核心数据结构：**
    *   **`PipelineExecutor`**: 负责多线程调度。采用基于 Pull/Push 状态机的多线程调度模型，唤醒准备好数据的 Processor 进行计算。
    *   **`Block`**: 数据在 `IProcessor` 之间流转的**基本载体**。一个 Block 包含多列数据（一小批记录，默认通常约 65536 行）。
    *   **`ColumnWithTypeAndName`**: `Block` 内部的结构，包含了列的实际数据指针 (**`IColumn`**, 比如连续在内存中的数组)、类型 (**`IDataType`**) 和列名。所有的过滤 (`FilterTransform`) 和计算都是以 `IColumn` 为单位进行 SIMD（单指令多数据流）向量化运算的。

### 流程总结 (针对 SELECT ... WHERE)

1. **SQL String** `-> (IParser)` `->` **ASTSelectQuery**
2. **ASTSelectQuery** `-> (InterpreterSelectQuery)` `->` **QueryPlan** `(ReadStep -> FilterStep -> ExpressionStep)`
3. **QueryPlan** `-> (buildQueryPipeline)` `->` **QueryPipeline** `(MergeTreeProcessor(s) -> FilterTransform(s) -> ...)`
4. **QueryPipeline** `-> (PipelineExecutor)` `->` 调度 Processor，使得 **Block (列存数据块)** 在内存中快速流转和计算，并返回结果。
